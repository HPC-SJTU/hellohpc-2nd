# MahjongX

## 题目说明

`src/` 提供分析程序 `system` 的基准实现．你的任务是在高性能计算平台上加速该程序，不得改变其数学含义和协议输出．

`system` 必须支持以下命令：

```sh
system full_analyze <setup_match_file> <mask>
```

程序从标准输入读取牌谱．参数 `<setup_match_file>` 指定对局和策略配置文件，参数 `<mask>` 指定需要分析的玩家．

`mask` 是玩家位掩码，第 $i$ 位表示是否分析玩家 $i$．一次分析是对一名玩家当前局面的分析．正式评测使用的掩码为 `15`，即分析全部四名玩家．

程序逐事件处理牌谱．一个事件是牌谱中的一条逻辑记录．`DRAW` 事件触发一次对摸牌玩家的分析．`DISCARD` 和 `UPGRADED_KAN` 事件分别触发对其余每名玩家的分析．

对于有两个及以上候选项的局面，程序向标准输出写入一个 `POS` 候选块．候选项是玩家的一组合法动作序列．候选块包含 `POS` 头、`CAND` 记录、对应的 `ACTION` 序列和可选指标．

实际动作确定后，程序写入对应的 `ACTUAL` 结果块．结果块以 `ERR_OK`、`ERR_UNMATCHED` 或 `ERR_UNOBSERVED` 结束．

进度标记用于表示一次分析已完成．程序必须为每次要求的分析向标准错误输出写入一条 `FULL_ANALYZE_STEP` 标记．

目标机器是配有 128 核鲲鹏 920 处理器的 AArch64 机器．正式测试的牌谱和配置文件均合法，且格式正确．

## 编译与测试

在集群上的仓库根目录运行：

```sh
bash build.sh
bash judger/provision.sh
```

上述命令生成 `src/system`、`checker/build/checker` 和 `interactor/build/interactor`．Boost 1.84.0 位于 `/vault/public/xflops/boost`．

你可以修改 `build.sh` 以使用其他编译器．如果编译器需要额外的运行库，也要在 `run.sh` 中加载对应环境．

### 提交脚本

评测器先运行一次 `build.sh`，再为每个输入调用 `run.sh <setup-file>`．编译时限为 10 分钟，每个输入的运行时限为 2000 秒．

两个脚本均可修改，且都从仓库根目录运行．`build.sh` 中的环境变更不会保留到 `run.sh`．

### 交互器

正式评测必须使用交互器 `interactor`．交互器负责逐事件向程序发送牌谱，并检查进度标记．其调用方式为：

```sh
<interactor> <game-record> <mask> -- <submission-command> [args...]
```

评测器使用 `run.sh` 启动提交程序：

```sh
<interactor> <game-record> 15 -- bash run.sh <setup-file>
```

交互器每次向提交程序的标准输入写入一个事件．如果该事件需要分析，交互器会等待全部预期的进度标记，再发送下一个事件．交互器将提交程序的标准输出和标准错误输出分别转发到自己的对应输出．

每个输入通过以下接口传给程序：

| 接口 | 内容 |
| --- | --- |
| `run.sh` 的标准输入 | 当前测试的牌谱，逐事件传入． |
| `run.sh` 的第一个参数 | 当前测试的对局和策略配置文件路径． |

掩码固定为 `15`．`run.sh` 只负责设置 CPU 绑定、环境变量、程序路径和参数，然后启动程序．`run.sh` 不得调用交互器，也不得从文件读取测试牌谱．

程序的标准输入是管道，不支持定位或回退．程序必须逐事件读取牌谱，并立即向标准错误输出写入进度标记．不得一次性读完整份牌谱，也不得将输出延迟到输入结束．

### 公开自测

`sample/` 包含公开样例算例和配置文件．运行以下命令编译并测试代码：

```sh
hellohpc test
```

该命令只运行公开样例算例，其得分不是排行榜得分．编译后，也可以单独测试一个输入：

```sh
./interactor/build/interactor sample/game_record_game1.txt 15 -- \
  ./run.sh sample/setup_match.txt > submission.out 2> submission.err
./checker/build/checker sample/game_record_game1_full_analyze.txt submission.out
```

检查器 `checker` 将程序的标准输出与参考输出比较．违反交互协议会导致交互器报错，提交得零分．

### 计时

每个输入的计分用时取标准错误输出中最后一条有效 `FULL_ANALYZE_STEP` 标记的 `ELAPSED_SECONDS` 值．`STEP_SECONDS` 和程序内部各阶段的计时仅用于诊断．

计时从程序请求第一行牌谱之前开始．对局配置和策略初始化在计时开始前完成．

## 规则

- 结果以官方检查器为准．浮点数的绝对或相对误差不得超过 $10^{-4}$，包含边界值．
- 局面、候选动作、可选字段的有无、实际动作和错误状态必须一致．候选项的排列顺序不影响匹配．
- 程序必须支持所有合法事件、动作、策略、赤牌、隐藏牌、轮次边界．
- 不得针对固定测试、牌谱、随机种子、事件、玩家或参考输出来编写特例．
- 基准实现中使用 32 位及以上浮点数进行计算和数据传递的部分，不得改用低于 32 位的浮点数．
- 不得提前 `ELAPSED_SECONDS` 的计量时刻．基准实现中原本在该时刻之前完成的所有运算和逻辑，优化后仍必须在该时刻之前完成，不得移至计量之后．
- 必须保留完整的数学模型和合法分支，且输出必须通过检查器．

## 计分

正式评测运行四个输入．game1 和 game2 公开，game3 和 game4 隐藏．四个输入都必须通过交互器和检查器．

总用时 $T$ 为四个输入最后一条 `ELAPSED_SECONDS` 的和，单位为秒．编译和检查器的运行时间不计入总用时．

控制线为 1000 秒，零分线为 2000 秒．设排行榜上最快的有效提交总用时为 $T_{\mathrm{best}}$，满分用时为 $F=\min(T_{\mathrm{best}},1000)$．得分公式为：

$$
\mathrm{score}=100\times\max\left(0,\min\left(1,\frac{F(2000-T)}{T(2000-F)}\right)\right)
$$

总用时不超过 $F$ 得 100 分，达到或超过 2000 秒得零分．榜首用时降低后，满分用时也可能降低，1000 秒不是固定的满分线．编译失败、超时、协议错误或答案错误均使整个提交得零分．

CLI 自测固定使用 $F=1000$，仅供参考，最终以正式评测结果为准．

基准实现运行较慢，得到零分或很低的分数属于正常现象．

## 提交

运行以下命令生成提交包：

```sh
hellohpc pack --output submission.zip
```

提交包包含 `build.sh`、`run.sh` 和 `src/` 中的源文件，不包含测试数据或评测程序．将 `submission.zip` 提交到平台．
