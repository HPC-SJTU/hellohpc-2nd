# 核场响应加速

## 黑塔的模拟宇宙

在黑塔空间站的模拟宇宙深处，黑塔用 $C$ 组场参数搭起了一片奇怪的“核场”。她特意强调：“这里的‘核’不是星核，不是原子核，更不是螺丝咕姆的机械核心，只是一组用来算响应的函数项。谁再传谣，我就把谁塞进差分机里跑一万轮。”

螺丝咕姆优雅地旋转齿轮：“已记录。每组核包含高斯距离项与方向正弦项。高斯距离项由中心 $\mu_c$、权重 $w_c$、距离尺度 $s_c$ 控制；方向正弦项由系数 $b_c$、缩放系数 $t_c$ 和投影向量 $v_c$ 控制。注意，$b_c$ 乘在正弦函数外面，不是加到结果上的偏置；方向正弦项也不使用中心 $\mu_c$。各组核在 $D$ 维空间中的每个查询点产生的响应会相加。”

阮·梅把一份数据投影到空中：“我们需要在 $Q$ 个查询点上计算总响应。每个查询点 $x_q$ 都要和全部 $C$ 组核作用，把这 $C$ 组贡献相加后得到一个数。$D$ 是 $16$ 或 $32$，$Q$ 最大约为 $10^5$，$C$ 最大约为 $10^4$。开拓者，这不是查找最近邻，也不是找星核——只是公式。”

黑塔不耐烦地敲了敲屏幕：“所以，去把 `compute_field` 加速。要是能在星穹列车到站前算完，我就允许你在模拟宇宙里多抽一次祝福。”

于是，为了不让模拟宇宙坍缩成一锅量子乱炖，开拓者接过 `points`、`centers`、`weights`、`scales`、`bias`、`trig_scale`、`trig_vec`，开始了一场 CPU 上的核场响应竞速。

## 背景与术语

本题可以理解为：给定 $C$ 组场参数，在 $Q$ 个位置上分别计算这些参数叠加后的响应值。这里的“核”指一组用于计算响应的函数项，与原子核无关；每个待计算的位置称为**查询点**。“查询”不是查找或最近邻搜索，而是在指定坐标处计算公式的值。查询点和其他向量都有 $D$ 个分量。

第 $q$ 个查询点记为 $x_q$。对于第 $c$ 组参数，先计算：

$$
r_{q,c} = \lVert x_q-\mu_c\rVert^2
= \sum_{d=0}^{D-1}(x_{q,d}-\mu_{c,d})^2,
$$

$$
p_{q,c} = x_q\cdot v_c
= \sum_{d=0}^{D-1}x_{q,d}v_{c,d}.
$$

这一组参数对查询点产生两部分贡献：

- 第一项 $G_{q,c}=w_c\exp(-s_c r_{q,c})$ 称为**高斯距离项**。中心点 $\mu_c$ 决定它的位置，$w_c$ 决定贡献的大小和正负，$s_c$ 控制贡献随距离变化的快慢。
- 第二项 $H_{q,c}=b_c\sin(t_c p_{q,c})$ 称为**方向正弦项**。投影向量 $v_c$ 与缩放系数 $t_c$ 共同决定它随查询点变化的方向和快慢，$b_c$ 决定贡献的大小和正负。这一项不使用中心点 $\mu_c$。

最终把全部 $C$ 组贡献相加，每个查询点得到一个数：

$$
\operatorname{out}[q]=\sum_{c=0}^{C-1}(G_{q,c}+H_{q,c}).
$$

## 编程任务

给定 $Q$ 个查询点和 $C$ 个核中心，实现并尽可能加速 `src/solver.py` 中的：

```python
def compute_field(points, centers, weights, scales, bias, trig_scale, trig_vec):
    ...
```

输入均为按行连续存储（C-order）的 `numpy.float32` 数组：

| 函数参数 | 数学符号 | 形状 | 含义 |
| --- | --- | --- | --- |
| `points` | $x_q$ | `(Q, D)` | $Q$ 个查询点 |
| `centers` | $\mu_c$ | `(C, D)` | 高斯距离项的 $C$ 个中心点 |
| `weights` | $w_c$ | `(C,)` | 高斯距离项的系数 |
| `scales` | $s_c$ | `(C,)` | 高斯距离项的距离尺度 |
| `bias` | $b_c$ | `(C,)` | 方向正弦项的系数，不是最终结果上的全局偏置 |
| `trig_scale` | $t_c$ | `(C,)` | 点积进入正弦函数前的缩放系数 |
| `trig_vec` | $v_c$ | `(C, D)` | 方向正弦项的投影向量，不要求是单位向量 |

必须返回形状为 `(Q,)`、dtype 为 `numpy.float32` 的 NumPy 数组，并且不得包含 `NaN` 或正负无穷。正式数据中 $D$ 为 $16$ 或 $32$，$Q$ 最大约为 $10^5$，$C$ 最大约为 $10^4$。

## 正确性

评测严格检查输出长度、形状、dtype 和有限性。对于每个元素，设选手输出为 $a$、参考值为 $b$，必须满足：

$$
|a-b|\le \mathrm{atol}+\mathrm{rtol}\cdot|b|,
$$

其中 $\mathrm{rtol}=10^{-4}$、$\mathrm{atol}=10^{-5}$。两个容差会相加形成允许误差，不是两个独立条件，也不是满足其中任意一个即可。参考值接近 $0$ 时主要由 `atol` 提供容差；参考值绝对值较大时，`rtol` 会按 $|b|$ 增加容差。所有输出元素都满足上式，正确性检查才通过。

四个正式正确性用例各 $5$ 分，共 $20$ 分。任一前置正确性检查失败，后续性能用例不会执行。

## 性能与计分

正式评测使用单节点 **32 个物理 CPU 核、64 GiB 内存**，不提供 GPU。内存限制涵盖选手进程及其所有后代进程。环境初始化和模块准备各限 5 分钟，不计入性能分；正式调用之外的导入不计分。正式评测先加载提交的 `env.sh`，再进行准备与测试。

正式评测不运行零分 `sample`。四个正确性用例各 5 分，每个用例的正式 `compute_field` 调用限 **5 秒**；在时限内通过正确性检查才得分，否则该项为 0 分。前置用例失败后停止后续测试。**直接提交仓库原始的 Python 代码与默认 env.sh，会在正式正确性用例超时，无法获得分数，需要先优化。** `sample` 仅供本地理解接口，能通过它不代表能获得正式分数。

两个性能用例各启动 3 个全新 Python 进程。每个进程先用最多 2048 个查询点、48 组核参数（维度不变）预热一次，再调用 `compute_field` 处理正式输入。预热输入不是完整正式输入，禁止在准备或预热阶段提前计算正式答案。正确性用例不预热，只运行一次正式调用。

**计分只测正式 `compute_field` 函数调用，取三次调用 wall time 的最大值，不取平均值。** 函数内的计算、分配、转换、线程调度及本次调用触发的编译等均计入；评测器的环境初始化、导入、读入数据、预热、答案检查和保存结果均不计入性能分。函数必须同步完成全部工作后返回，不能把计算移到计时区间之外。

```text
准备环境、导入、读入数据 → 小输入预热（均不计分）
→ 开始计时 → compute_field(正式输入) → 返回 → 停止计时
→ 检查并保存答案（不计分）
```

时间由外部评测进程记录，开始/结束通知带来少量进程通信与调度开销，不使用选手自行报告的耗时。禁止修改或伪造评测通信、计时及结果协议。

函数调用时限与总保护时限分开：正确性调用限 5 秒，性能调用限 70 秒；每个 worker 从启动到结果保存总共限 120 秒。正确性评测步骤总限 150 秒，性能步骤（3 个 worker）总限 420 秒。任一时限超出均不得分；这些总时限是资源保护，不是计分时间。

| 用例 | 分值 | 满分时间 | 有分时间条件 |
| --- | ---: | ---: | --- |
| c-small-d16 | 5 | 正确性通过即满分 | 正式函数调用在 5 秒内完成且答案正确 |
| c-mid-d16 | 5 | 正确性通过即满分 | 正式函数调用在 5 秒内完成且答案正确 |
| c-mid-d32 | 5 | 正确性通过即满分 | 正式函数调用在 5 秒内完成且答案正确 |
| c-large-d16 | 5 | 正确性通过即满分 | 正式函数调用在 5 秒内完成且答案正确 |
| large-a | 30 | 500 ms | 答案正确且计分时间小于 12000 ms |
| large-b | 50 | 1200 ms | 答案正确且计分时间小于 35000 ms |

W 是该用例分值，T 是实测计分时间，T_full 是满分时间，T_max 是零分时间，三个时间必须使用同一单位，ln 表示自然对数，计分规则：

```text
T <= T_full: score = W
T >= T_max:  score = 0
其他情况:   score = W * ln(T_max / T) / ln(T_max / T_full)
```

只有答案正确才计算时间分。总分为正确性 20 分与性能 80 分之和；跳过的用例记 0 分。
